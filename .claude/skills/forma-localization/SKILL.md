# The localization format

The runtime lives in the sibling Forma repository as `Forma.Framework.Localization` and its `.Json` implementation; this linter compiles against it and must never re-implement its parsing. What follows is the shape of the data the rules read. The rule-by-rule authority is `docs/linting-rules.md`.

## Lookups

- A consumer injects `IStringLocale<T>` and reads strings as `L["A sentence in the source language"]`; the key **is** the source text, in the language `SourceLanguage` names, English by default, and an absent entry falls back to the key, silently.
- A lookup takes one form: a literal key with values paired to its distinct holes by position, in the order the holes first appear — `L["Stored {stored} of {total}.", written, allowed]`. A wrong count throws (LOC0201).
- An interpolated key — `L[$"…{stored}…"]` — formats before the lookup, so the runtime receives the formatted text as the key and no entry matches it; LOC0211 reports every such callsite as an error.
- Consumers name holes in PascalCase as a matter of style; the linter does not enforce it, and no rule should start to — a hole name is legal wherever the runtime reads it.

## Files

- A type's entries are read by the type's **full name**, never from where a file sits, which is the drift LOC0112 exists to catch. The default reading takes a locale file wherever it sits: a folder and a dot separate a name alike, the folder of locale files, `.locales`, or for an assembly's own types the one its `.locale.json` names as `localesDir`, is left out wherever it stands, the culture is the first part written exactly as .NET names a culture, and the rest is the name the file stands for, counted from where the assembly's names begin, so `Components/Bars/.locales/he.json`, `.locales/he/Components.Bars.json` and `Components/Bars.he.json` all stand for `Components.Bars`, whose nested objects are sections completing the rest of a type's name; a file named for a type, `Components/Bars/.locales/FormaToolbar.he.json`, holds that type's entries at its top level. A top-level section whose name starts with `@.` names a type from the assembly's root wherever the file sits, `@.Components.Bars.FormaToolbar`. A folder is a namespace, never a type, which LOC0118 holds a project to. The one optional `.locale.json` a project embeds at its root may state `paths` that replace the default reading for the assembly's own files, as the linter's own `.locali.json` is one per run. A pack's file, and an application's for another assembly, starts its name with that assembly's, the culture before it or after it, and goes on from the root namespace that assembly declares.
- The runtime counts a type's name from the root namespace its `.locale.json` declares, or from the assembly's name where it declares none, and never reads the project's `RootNamespace`; a type outside that root is read by its full name. LOC0023 reports a root no type of the project is under, the drift a rename of one leaves.
- The runtime's walk, `LocaleSource` in `Forma.Framework.Localization`, is the only authority on which file a type reads; the linter runs that walk over the project tree through `ProjectLocaleSource`, and over a pack's files and an application's for other assemblies through `AssemblyNamedLocaleSource`, and never re-derives the layout; `LocaleFileNames` is the one reading of a file's name.
- The file's first property is the metadata entry: `"$localization": "SchemaVersion: 1.0.0; Culture: he;"` — required fields in that order, and the culture must agree with the one the file's name gives it: the first part of the name, folders included, that is a culture written exactly as .NET names it, a folder, `.locales/he/Components.json`, or the end of the file's name, `Components.he.json`.
- Every other property maps source text to its text in the file's culture, or holds a section. A JSON `null` value declares that the key's right text *is* the source text; the runtime reads it as found, which differs from absent wherever a caller can tell (`ResourceNotFound`, `RequireMatchingLocalization`, `GetAllStrings`).
- A parent culture answers for its children: `.locales/es-419.json` may carry only what differs from `.locales/es.json`, and only a key neither declares is missing.
- An application's file whose name starts with an assembly's name localizes that assembly's types, as `.locales/Forma.Blazor/Components/Bars/he.json` or `.locales/he/Forma.Blazor/Components.Bars.json`. The build embeds it under the project's root namespace as it does every locale file, unless a project file copies it beside the application, which makes it a host's file. LOC0112 and LOC0120 hold an application's such file to that assembly's types where a project of the run builds it, LOC0112 reports a library's such file, which nothing reads by that name, and the file rules read a host's file. The project's `EmbeddedResource` items decide which files are embedded, and the build's own naming decides the name each is read by.
- Two files of one source standing for one name in one culture are both read, as `.locales/he/Components.json` and `Components/.locales/he.json` are. A source reads one entry per key: a type's own over a shared one, and of two files giving one entry different texts, the one whose name sorts last, ordinally; LOC0120 reports such a conflict where a type reads the entry.
- A file leads with its reserved entries in order: `$localization`, then `$shared`, the section whose entries every type the file reaches gets and which holds entries alone, so a `$shared` that is not an object or that nests a section fails to load and LOC0116 reports it; LOC0114 reports the order. A locale file holds entries and nothing a tool reads: a per-file exception to a rule is written in the linter's `.locali.json`, never in the locale file.
- A key shaped like a reserved entry, `$` followed by one lowercase word and nothing else, is the engine's; one the runtime does not define is reported by LOC0115 in a file, at any level, and by LOC0212 at a callsite. `$$` escapes the shape, dropping one `$` and reading the rest as text, and any other `$` text, such as `$`, `$ per month`, `$5 off`, `$USD`, `$camelCase`, or `$price/month`, is ordinary source text.

## Holes and expressions

- A brace hole `{Name}` names a value; a repeated name still takes one value, because that is how the runtime pairs them.
- A plural expression names its argument in brackets: `[$ plural; one: # file; other: # files; $][count]` — `#` renders the count, and `other` is the category the rest fall back to.
- A brace hole and a bracketed plural argument are equivalent ways of naming a value, so a key and its text may mix them freely.
- Escaped braces are literal text, and brace text containing a space is prose the runtime renders as written.
- Do use the runtime's own `LocalizedFormat` parsing (through `HoleNames`) to read the names a format refers to; scanning for braces by hand re-implements the runtime and will disagree with it.
